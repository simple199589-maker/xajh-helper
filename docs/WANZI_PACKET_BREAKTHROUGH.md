# 丸子封包直发能力突破复盘

> 日期：2026-08-06  
> 当前实现：`app/core/wanzi_packet.py`  
> 接入位置：`app/core/hang_settings.py`、`app/ui/pages/_impl.py`

## 1. 最终结果

本次突破不是继续模拟“使用背包道具”，也不是直接向 socket 重放密文，而是还原游戏进程内部已经存在的**系统命令发送入口**，按游戏实际接受的顺序直接提交一组完整的丸子命令。

最终实现具备以下能力：

- 完全脱离对照脚本运行；
- 不占用、不修改恢复道具槽；
- 支持内功丸子、外功丸子两种互斥模式；
- 一次逻辑释放严格按 `P1 -> P2` 串行发送；
- 活跃阶段每次发送一组完整的 `P1/P2`，然后只等待用户频率；
- 使用 18m 怪物 AOI 门控，稳定无怪和切图期间停包；
- 挂机释放与手动释放按 PID 共享一个串行发送器，以 owner 独立持有和释放；
- 所有游戏调用共用应用级 `Call` 互斥锁，避免和其他远程调用竞态。

## 2. 为什么最初的路线没有效果

最初沿“道具使用上限/恢复槽”方向修改后，调用表面成功，但实战伤害没有明显增加。问题在于：

1. 道具槽路径只覆盖了正常 UI/背包消费流程，不等于真正的技能命令直发路径；
2. 只观察函数返回值，不能证明服务器侧产生了有效伤害；
3. 直接重放网络密文也不可取，会话加密是连续状态，历史密文不能当作固定明文模板重复发送；
4. 游戏实际需要的不是一个孤立包，而是一组有顺序的 `P1/P2` 系统命令。

因此验证标准从“函数是否返回成功”改为：

```text
游戏画面是否连续产生有效伤害
  + 长时间运行后是否仍可继续释放
```

## 3. 真正的突破点

### 3.1 用可复现行为做黑盒对照

先让一个已知可以稳定直放技能的对照脚本运行，再只观察它对游戏进程做了什么。关键现象是：

- 一次完整释放对应两次系统命令调用；
- 两次调用组成固定的 `P1 -> P2` 对；
- 组内串行，不需要并发；
- 每一组完整命令之后需要间隔；
- 原对照脚本把一次短暂停顿放在每个完整命令对之后，并以 300 秒作为活跃窗口。

这一步把问题从“猜包/猜道具逻辑”收敛成了：

```text
找到系统命令入口
  -> 还原调用约定
  -> 取出 P1/P2 明文字节
  -> 在自己的进程控制代码中重建同等调用
```

### 3.2 找到游戏内部发送入口

当前版本的关键地址为：

| 名称 | 地址/偏移 | 作用 |
|---|---:|---|
| `ROOT_GLOBAL` | `0x015282D8` | 游戏全局根指针 |
| `THIS_OFFSET` | `+0x2C` | 从根对象取得系统命令对象 |
| `SEND_TARGET` | `0x00CD1740` | 游戏内部系统命令发送函数 |
| 原始入口前缀 | `64 A1 00 00 00 00` | 调用前检查入口未被残留钩子修改 |

还原出的 32 位调用桩等价于：

```asm
push 38                         ; 包长度
push packet_address             ; 38 字节明文地址
mov  edx, [0x015282D8]
mov  ecx, [edx+0x2C]            ; this
mov  eax, 0x00CD1740
call eax
ret
```

这说明最终能力不需要自己实现 socket 层加密。明文交给游戏内部函数后，仍由游戏当前会话的正常网络栈完成排队、加密和发送。

### 3.3 还原完整命令对

当前版本使用三段 38 字节明文：

#### 外功 `P1`

```text
1F0000000000005F0A0103010001420000000000000000000060C0FCC162FD7242E09E86C201
```

#### 内功 `P1`

```text
1F0000000000005E0A01036300004200000000000000000000AC9303C262FD72428A7481C201
```

#### 公共 `P2`

```text
1F0000000000005D0A01020800FF4100000000000000000000268B97C28D8A7A42A212C4C301
```

外功与内功只切换第一段 `P1`，第二段始终使用公共 `P2`。发送器只把完整的 `P1/P2` 视为一对，绝不交叉并发。

## 4. 如何独立重建发送能力

`_send_packet()` 对每个 38 字节命令执行以下步骤：

1. 获取该 PID 的应用级 `Call` 互斥锁；
2. 检查目标进程仍允许安全远程调用；
3. 读取 `0x00CD1740` 的入口前缀，发现被钩住就拒绝发送；
4. 在游戏进程中申请一页可执行内存；
5. 写入 38 字节明文和 24 字节调用桩；
6. 刷新指令缓存；
7. 以挂起状态创建远程线程，再显式恢复执行；
8. 安全等待线程结束并读取返回值；
9. 仅在线程已确认结束后释放远程内存；
10. 超时时不强行释放可能仍在执行的内存，而是立即停止后续发送。

最重要的稳定性原则是：**不能在线程状态未知时释放远程代码页，也不能让多个功能同时进入游戏调用链。**

## 5. 频率是怎样压出来的

### 5.1 失败现象

早期持续压测时，短时间看起来能够发送，但运行一段时间后游戏会出现：

- 后续任何丸子使用都不再生效；
- 停止脚本也不能自行恢复；
- 必须重新登录才能恢复发送能力。

这说明限制不只是单次函数返回值，而是游戏内部消费能力和节奏。只追求最短间隔会把内部状态打死。

### 5.2 当前节奏

发送器按对照脚本的阶段节奏完全串行运行。原脚本的 `停顿:6000`
不是“永久休眠”语义；正式实现把它改造成低频保活发送阶段，避免出现
完全空窗，同时不把这 6 秒混同为活跃批次之间的尾等待：

```text
低频阶段（6 秒）：
  每秒 3 对：P1 -> P2 -> 等待约 333ms

活跃阶段（300 秒）：
  P1 -> P2 -> 等待 interval_ms
  继续下一对

300 秒到期 -> 回到下一次低频阶段
```

其中：

```text
low_rate_seconds          = 6
low_rate_pairs_per_second = 3
active_window_s           = 300
```

配置默认值为：

```text
interval_ms = 100
```

频率输入值就是活跃阶段每个完整 `P1/P2` 对之后的等待时间。对照脚本按
6 对分段，只是为了周期执行“判断记录时间/判断附近怪物”；它不构成独立的
限速。当前 AOI 已由调度中心异步持续检测，因此删除了没有实际意义的“每批”
参数和人工批尾，只保留一个可直接理解、可实测调整的频率。

## 6. 为什么移除发送队列门控

调研阶段曾持续读取 `connection+0xB8` 的待发送队列。一次实测结果为：

```text
elapsed=118.158s
samples=76197
invalid=0
peak_pending=1
busy_entries=114
longest_busy_ms=3.554
nonzero_ratio=0.001601
enqueue_observed_lb=114
consume_observed_lb=114
```

该队列中的命令进入后通常在数毫秒内就被网络层取走，`pending` 不能代表
服务器是否消费，也不能可靠反映技能是否仍有效。用它控制发送只会增加一次
高频 RPM、缓存状态机和误停风险。因此当前实现已删除队列探测、队列缓存、
降频/停包门控及其日志；长期稳定性只通过一个明确的发送频率来调节。

## 7. 18m 怪物 AOI 门控

为了减少无意义释放，挂机模式增加了纯 RPM 的附近怪物探测：

- 默认半径：18m（实测丸子最大攻击距离约 19m，预留 1m 安全边界）；
- 扫描周期：200ms；
- 扫描对象：当前场景的 `CECNPC` 哈希表；
- 通过怪物虚表过滤服务 NPC，避免普通 NPC 错误开门；
- 发包线程只读缓存，不在发送线程里扫描内存；
- 发现怪物立即放包；
- 连续两次稳定确认无怪后停包；
- 暂时没有有效 AOI 结果时允许放包；
- 明确处于切图/场景不稳定状态时立即停包；
- 短暂读取失败使用最近稳定缓存，避免门控抖动造成画面卡顿。

AOI 读取放在 `safe_dispatch` 调度中心，以 `P2/RPM` 周期任务运行。发包线程
只读取门禁缓存，不执行内存遍历，因此不会堵住整个助手。

## 8. 手动释放与挂机释放的共享 owner

每个 PID 同一时间只创建一个串行 `WanziPacketRunner`：

- `manual`：用户点击“开启/关闭释放丸子”；
- `hang`：挂机开关自动持有。

两种 owner 可以共同持有同一个 runner，因此不会出现两条发包线程争用。手动释放不依赖挂机开启，可以独立运行；开启或关闭任一功能只增删自己的 owner，另一方仍持有时 runner 不停止，仅最后一个 owner 离开时才真正销毁。

挂机临时暂停（例如切场景）时只暂停 `hang` 门禁；若 `manual` 仍持有，独立释放继续使用同一个串行 runner。开启手动释放绝不能通过 `stop_hang()` 硬关原生挂机。

## 9. 调试过程中最重要的事故教训

本次调研中，长时间挂着会持续命中的断点曾导致调试器和游戏一起崩溃。后续采集必须遵守：

```text
创建断点
  -> 命中并采集最小必要信息
  -> 继续运行
  -> 如需复用则再次命中、再次继续
  -> 采集完成后立即删除断点
  -> 再执行一次继续，放开当前暂停状态
  -> 然后才离开现场分析日志
```

严禁：

- 把持续高频命中的断点留在游戏里，然后长时间离开分析；
- 同时挂一批断点等待事后慢慢筛；
- 只禁用脚本而不确认当前线程已经继续；
- 在线程暂停时认为“游戏暂时没反应”只是正常现象。

断点是一次性采样工具，不是长期监控工具。长期状态应改用 RPM 采样、日志钩子或独立监控脚本。

## 11. 版本升级后的复验清单

这些地址和结构都属于当前游戏版本，客户端更新后不能盲信旧值。至少复验：

1. `ROOT_GLOBAL` 是否仍为 `0x015282D8`；
2. 系统命令对象是否仍位于根对象 `+0x2C`；
3. `SEND_TARGET` 是否仍为 `0x00CD1740`；
4. 入口前缀和调用约定是否变化；
5. 三个 38 字节命令长度和字段是否仍有效；
6. AOI manager、对象坐标和怪物虚表是否变化；
7. 用单次人工实战确认伤害；
8. 最后才进行一分钟及更长时间的持续压测。

复验时仍应坚持：一次只改一个变量，先证明一条最窄的 `P1 -> P2 -> 有效伤害` 链路，再扩大压测范围。
